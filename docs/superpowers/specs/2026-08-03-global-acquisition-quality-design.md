# LeadFlow 单人版全局获客质量提升设计

**日期：** 2026-08-03

**状态：** 最终设计，待书面确认后进入实施计划

**基线：** `fix/acquisition-result-quality` / `b165deb`
**范围：** 全国家、全行业通用的发现、验证、证据、任务结果与人工反馈机制

## 1. 背景与审核结论

墨西哥摩托车配件任务是第一个真实回归样本。它发现了十家候选，但大量候选停在官网不可达、结构化提取失败、国家未知或联系方式未落库状态。这个样本证明当前验证与恢复链路存在缺口，但不能被当作全局成功率基线，也不能催生墨西哥专用规则。

两轮外部审核中的下列问题在当前基线仍成立：

- 有候选待补证的任务仍可能被技术状态显示为 `failed`；
- 国家信号、联系方式和实体类型没有充分利用已保存的公开证据；
- 失败归因、批量恢复和用户行动指引不足；
- 当前去重主要限于单 Mission，跨任务重复发现和重复验证仍可能浪费预算；
- 查询产出、重复率、验证率和接受率尚未形成稳定反馈统计。

下列审核结论基于旧提交，在当前基线已经过期：

- 后台重评覆盖人工终态：当前使用原子条件更新保护 `accepted`、`promoted`、`rejected`；
- provisional 可获 S 级：当前 provisional 最高为 B，纯证据模式不生成客户优先级；
- HTML 隐藏节点导致 `AttributeError`：当前已有修复和回归测试；
- MiMo schema 失败没有定向修复：当前 `_validated_request` 已执行一次安全 schema 修复请求，并测试第二次无效时安全失败。

仍未实现的是 schema 修复失败后的预算内延迟重分析、用量统计和任务级失败归因，这些属于本设计的新工作。

## 2. 目标

1. 所有国家使用同一套可解释证据信号框架，不写国家专用业务分支。
2. 公开网页即使 AI 提取失败，也尽量产出确定性联系方式、国家信号和可操作缺口。
3. 商会、目录、政府、媒体等非客户实体尽量不消耗官网验证预算，同时避免关键词硬删真实企业。
4. 将任务的后台执行状态与用户看到的业务结果分开，旧任务也能得到正确展示。
5. 对网络、网页、结构化输出和队列问题采用有界恢复，禁止无限重试和静默追加费用。
6. 先提供只读效果统计，再引入需人工批准的策略学习；不让一次错误反馈污染全局。
7. 保留租户隔离、证据版本、人工接受后才进入 CRM、研究阶段不自动外发等既有边界。

## 3. 非目标

- 不为墨西哥、摩托车或西班牙语编写专用判定代码。
- 不让 MiMo 直接修改生产评分权重、搜索策略或排除策略。
- 不依赖运行时国家查询 API。
- 不在本轮实现 LinkedIn 浏览器自动化、MCP 抓取或自动外联。
- 不在一个 PR 内同时完成信号融合、全局实体主数据、反馈回放引擎和整站 UI 重构。
- 不保存模型思维链、原始错误响应或可能包含敏感信息的异常正文。

## 4. 方案选择

### 4.1 不采用：样本规则补丁

直接使用 `.mx`、`mexicana` 或西班牙语关键词能快速改善当前样本，但会过拟合，无法覆盖巴西、德国、美国及跨境企业。

### 4.2 采用：全局信号融合与分阶段反馈治理

确定性证据解析负责国家、联系方式、实体类型和重复身份。MiMo 只处理需要语义理解的买家角色、产品相关性和复杂网页内容。策略反馈先统计、后建议、再由用户批准，不自动改写当前策略。

### 4.3 不采用：MiMo 全权自主调参

该方案难复现、难回滚、成本不稳定，也无法向未来公共 SaaS 用户解释为什么某家公司被确认、排除或提高优先级。

## 5. 架构边界

新增或强化五个相互独立的领域单元：

1. `BusinessResultResolver`：从 Mission、Candidates 和 Jobs 推导唯一业务结果。
2. `CountrySignalResolver`：将离线国家元数据和证据信号融合为国家结论。
3. `ContactExtractor`：从已抓取页面确定性提取联系方式及来源。
4. `EntityTriage`：将搜索结果分为企业、目录、协会、政府、媒体等类型。
5. `AcquisitionMetrics`：计算查询产出、重复、验证和人工决策统计。

这些单元返回纯数据结果，不直接发通知、不直接改 UI、不直接调用外网。服务层负责持久化，路由和模板只消费统一结果。

## 6. 任务执行状态与业务结果

### 6.1 两层状态

现有 Mission `status` 继续表示执行生命周期：

- `draft`、`queued`、`running`、`paused`；
- `completed`、`failed`、`cancelled`。

用户看到的业务结果由统一纯函数推导并写入 `retrospective_json`：

- `ready`：存在可审核或可进入 CRM 的候选；
- `needs_review`：存在待补证候选；
- `partial`：获得候选或证据，但部分后台任务失败；
- `no_results`：流程正常结束但没有候选；
- `failed`：规划、搜索或基础设施失败，且没有任何可操作候选或证据；
- `cancelled`：用户取消。

消费方不得自行重写映射。Mission 详情、HTMX 状态片段、工作台、通知和审计都调用同一解析器。

### 6.2 存量兼容

不修改历史数据。对于旧记录 `status=failed` 但存在候选或证据的任务，解析器仍显示 `partial` 或 `needs_review`。因此旧墨西哥任务无需数据迁移即可获得正确文案。

### 6.3 统一计数

停止在用户界面使用含义不清的 `usable candidates`，改为：

- 已发现；
- 待补证；
- 可审核；
- 可进入 CRM；
- 已排除；
- 验证失败；
- AI 分析失败。

## 7. 全局国家证据信号

### 7.1 离线元数据

ISO 国家代码、国家名称别名、国家域名、电话区号、常见货币和语言标签使用版本化静态数据文件。运行时不查询第三方国家服务。

被广泛通用化的 ccTLD（例如 `.co`、`.io`、`.ai`、`.tv`、`.me`）单独标记并降低权重，不能单独确认国家。

### 7.2 信号分层

强信号：

- 官方页面明确国家声明；
- 官方联系页的完整地址；
- 公开企业注册信息；
- 可验证的当地联系信息与地址组合。

中等信号：

- 非通用化国家域名；
- 电话国家区号；
- 当地货币与明确市场词；
- 多个独立官方页面的一致区域信号。

弱信号：

- 页面语言；
- 搜索查询中的国家；
- Mission 的目标国家。

弱信号只用于说明和排序，绝不参与自动确认。

### 7.3 判定

- 一个官方强信号，或两个独立中等信号且至少一个来自已验证官方证据，才能自动确认机会市场；
- 只有一个中等信号时输出 `likely`，候选仍为待补证；
- 强信号互相冲突时输出 `conflicting`；
- 总部国家和机会市场分别判断；
- `.com.cn` 企业可以被确认服务墨西哥，但不能因此把总部国家改成墨西哥。

每个结论包含信号代码、来源证据 ID、信号强度、数据版本和可解释摘要。UI 的国家冲突提示必须消费这一结果，不得另写判断。

## 8. 确定性联系方式提取

`ContactExtractor` 从 fetcher 已允许的页面内提取：

- `mailto:` 与正文邮箱；
- `tel:` 与正文电话；
- WhatsApp 链接和号码；
- 联系页面 URL；
- 与联系方式相邻的地址片段。

规则要求：

- 优先首页、联系页、关于页，受现有最多五页预算约束；
- 标准化大小写、电话号码和 URL；
- 去除 `example.com`、图片文件名、`@2x`、脚本片段和明显占位值；
- 每条联系方式保存来源 URL 和证据 ID；
- 确定性提取先于 MiMo，MiMo 只补充语义信息；
- 提取失败不得阻断后续 provisional assessment。

持久化继续使用 `contact_json`，新增向后兼容的 `items` 数组，每项包含 `kind`、`value`、`source_url` 和 `evidence_id`；旧的 `paths` 与 `email` 键在过渡期继续写入，避免影响现有 CRM 晋升逻辑。

## 9. 全球实体类型预筛

### 9.1 两层分类

第一层使用确定性特征：

- URL 路径和域名模式；
- 标题、摘要和组织名称中的多语言实体词；
- 政府域名、招聘路径、目录列表页等结构特征。

第二层仅对不确定结果使用现有 MiMo 语义输出或降级待核验，不为每条搜索结果增加独立模型调用。

### 9.2 分类结果

- `company`；
- `manufacturer_or_supplier`；
- `buyer_or_distributor`；
- `directory_or_marketplace`；
- `association_or_chamber`；
- `government`；
- `media_or_article`；
- `unknown`。

高置信非企业不进入官网验证队列，但可作为发现来源证据保留。`unknown` 不硬删除。Slice 3 通过新增 migration 为 Candidate 增加 `entity_kind` 与 `entity_kind_source` 字段；分类版本和支撑证据 ID 写入 assessment 输入。该结果逐步替代当前仅靠 `exclude_terms` 字符串命中的排除逻辑。

## 10. MiMo 有界恢复与用量

### 10.1 结构化输出恢复

当前已有：

1. 初始请求；
2. 一次只包含安全校验路径的定向 schema 修复；
3. 第二次仍无效时返回安全 `invalid_response`。

新增：当 Provider 整体健康、Mission 仍有验证与时长预算时，可排队一次延迟重分析。每个候选最多一次延迟重分析；不得把每次 Job 的内部请求与 Job 重试相乘成无限调用。最终失败时保留官方证据，生成 provisional assessment，并提示人工重试。

网络超时、认证、限额、搜索插件缺失、网页不可达、内容类型、schema 无效分别保留错误码。

### 10.2 预算

复用 Mission 的 `max_verify`、`max_seconds` 和现有 Job `max_attempts`，不新增全局付费预算字段。代码必须计算候选级剩余尝试次数，防止一次 schema 错误消耗三轮各两次模型调用。

### 10.3 用量

Provider 返回 token 或用量数据时记录；不返回时保持 `unknown`，不得估造。第一期指标以请求数、页面数、耗时和候选产出为主，成本指标只有在真实用量存在时才展示。

## 11. 跨任务去重与证据复用

### 11.1 首期

- 规范化发现 URL、最终跳转 URL 和主域名；
- 复用现有 Lead/Company 的 domain、email 和 suppression 查询；
- 同租户、同主域名、最近三十天内已有有效官方证据时默认复用，不重复抓取；新鲜期允许在 7–180 天内配置；
- 新 Mission 仍创建自己的候选关系，以保留目标画像和评分上下文；
- 同名企业不得仅凭模糊名称自动合并。

### 11.2 后续

公司别名、注册号、全球实体主数据和多分支关系放到后续实体记忆阶段，不进入首个实现切片。

人工拒绝的抑制范围由原因决定：

- `wrong_buyer_type` 默认仅当前画像或 Mission；
- `excluded_business` 可以建议租户级抑制，但必须人工确认；
- 抑制不删除已经进入 CRM 的客户。

## 12. 效果统计与反馈治理

### 12.1 第一阶段：只读统计

按 Mission、国家、查询和来源计算：

- 新候选数；
- 精确域名重复率；
- 非企业实体率；
- 官网验证率；
- 联系方式提取率；
- 待补证率；
- 可审核率；
- 用户接受率；
- 请求数、页面数和耗时；
- 用量可得时的 token 与成本。

第一阶段不修改搜索或评分策略。

### 12.2 第二阶段：建议与回放

当样本量达到最低门槛时，系统可建议：

- 增加或降低查询优先级；
- 增加实体排除规则；
- 调整买家类型或评分权重；
- 对重复率高、产出低的查询暂停使用。

建议必须：

- 在历史标注样本上离线回放；
- 显示预计新增、误删和样本量；
- 生成新策略版本；
- 由用户批准后仅影响新任务；
- 可回滚；
- 不重写历史评估。

## 13. 最小 UI 范围

首期只实现支撑正确决策的 UI：

- 统一业务结果徽章和文案；
- 任务失败/部分完成归因面板；
- 批量重新验证；
- `系统重试` 与 `我来补证` 两类明确动作；
- 已验证官网、仅搜索证据、网页不可达等人类可读证据徽章；
- 具体缺失项和国家冲突说明；
- 已拒绝候选收起无效推荐信息；
- 真正执行失败使用红色，部分完成使用橙色，待审核使用黄色或蓝色，人工拒绝保持中性；
- 最小只读任务列表，按业务结果分组；
- 所有 Acquisition 页面使用统一导航，并保留通知入口。

完整侧边栏重构、跨任务高级筛选、空态插画、任务模板和区域快捷选择不进入首期。

## 15. 测试矩阵

### 15.1 国家

- 墨西哥 `.com.mx` + 西班牙语 + 官方地址；
- 巴西 `.com.br` + 葡萄牙语 + 巴西电话；
- 德国 `.de` + 德语 + 欧盟跨境销售；
- 美国 `.com` + 美国地址；
- `.com.cn` 总部在中国但明确服务墨西哥；
- `.co` 被当作通用域名且无哥伦比亚证据；
- 全球企业总部与机会市场不同；
- 强信号冲突；
- 只有弱语言信号；
- 信息稀疏单页站。

### 15.2 实体与联系

- 商会、协会、政府、目录、媒体、招聘页；
- 真实经销商名称含有可能触发排除词的反例；
- `mailto:`、`tel:`、WhatsApp、正文邮箱和联系页；
- `example.com`、图片 `@2x` 和脚本伪邮箱；
- 同一联系方式多页面重复。

### 15.3 状态与恢复

- `failed + candidates` 旧任务显示 partial/needs_review；
- 无候选但流程成功显示 no_results；
- 无证据且基础设施失败才显示 failed；
- schema 初次无效、修复成功；
- 两次 schema 无效、延迟重分析成功；
- 超出候选预算不再重试；
- 人工终态不被重评覆盖；
- 批量重验幂等且租户隔离。

## 16. 指标定义

- 自动确认改判率 = 被人工改判的自动确认数 / 被人工审阅的自动确认数；
- 预判一致率 = 人工补证后与系统 `likely` 一致的数量 / 已人工补证的 `likely` 数量；
- 非企业进入率 = 进入验证队列的非企业数 / 进入验证队列总数；
- 跨任务重复率 = 被精确域名复用或抑制的发现数 / 总发现数；
- 验证率 = 获得有效官方证据的候选数 / 尝试验证的候选数；
- 联系方式提取率 = 获得至少一个有效联系路径的候选数 / 获得有效官方证据的候选数；
- 可操作率 = `eligible + needs_evidence` / 总候选数；
- 成本仅在 Provider 返回真实用量时计算，不用估算值冒充事实。

## 17. 安全、租户和回滚

- 所有查询、复用、统计和建议必须带 `tenant_id`；
- 静态国家数据只读且版本化；
- 证据复用不跨租户；
- 自动确认仍需达到可解释证据阈值；
- provisional 不能自动接受、晋升或发送；
- 策略建议默认 `proposed`，人工批准后生成新版本；
- 每项策略和解析器版本写入 assessment/audit；
- 关闭新解析器时可回退到现有 unknown/人工补证路径。

## 18. 完成标准
