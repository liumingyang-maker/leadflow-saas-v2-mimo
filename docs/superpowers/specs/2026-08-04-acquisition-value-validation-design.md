# LeadFlow 结果价值验证与转化提升执行方案设计

**日期：** 2026-08-04

**状态：** 待用户书面确认

**计划代号：** QV（Quality Validation）
**适用范围：** Acquisition Mission、Candidate/Evidence、手动 Radar 转候选、人工审核与 CRM 晋升边界

## 1. 决策摘要

LeadFlow 当前已经具备可控的手动研究、证据保存、候选判定、有限重试、人工审核和 Radar 基础能力，但真实 Mission 尚未稳定产出可审核客户。最新 PE 样本的业务漏斗为：发现 5 家、待补证 4 家、排除 1 家、可审核 0 家。下一阶段的中心问题不是继续增加渠道或自动化，而是提高“搜索命中转为可审核客户”的比例，并用可回放数据证明收益。

本方案采用“价值验证优先，附带最小工程收口”的执行方式：

1. 先统一发布基线和文档事实；
2. 再建立不少于 50 例的回放语料与 10–20 个真实手动 Mission 基线；
3. 按可测量收益实施国家与联系恢复、验证预算预排序、证据新鲜度和请求级用量；
4. 用任务漏斗、逐候选原因和对应操作改善人工工作流；
5. 最后完成外部试用所需的运行、安全和数据治理门禁。

后台定时、自动 CRM、自动外联以及新增 LinkedIn、Places、YouTube 等渠道均不属于本方案。

## 2. 已比较的执行路线

### 路线 A：价值验证优先，最小工程收口（采用）

先冻结一条可发布基线，再建立评测集和真实 Mission 基线。后续算法、UI 和运行改动必须证明对可审核率、准确率、成本或人工操作时间有改善。

优点是能尽快判断产品是否创造真实价值，避免继续堆积无法验证的功能；缺点是前期会投入时间建设语料和度量，而不是立刻增加新页面。

### 路线 B：工程稳定性优先

先集中处理分支、部署、监控、数据库和安全，再优化结果质量。

优点是运行底座更稳；缺点是系统可能非常稳定地输出 0 个可审核客户，不能优先解决用户价值问题。

### 路线 C：功能扩张优先

立即增加更多 Provider、后台 Radar、浏览器自动研究或自动外联。

优点是表面功能增长快；缺点是召回污染、成本和安全面同时扩大，并违反当前“只允许手动运行”的产品决定。因此拒绝。

## 3. 产品定位与北极星

本阶段将 LeadFlow 定位为：

> 用户手动启动研究后，系统在明确预算和安全边界内，提供少量但真实、目标市场明确、产品或买家角色有公开证据、存在可用联系路径、能够由人工审核的候选客户。

北极星指标不是发现候选数量，而是：

`每个 Mission 的可审核真实客户数`

辅助指标包括：

- 可审核候选准确率；
- 发现到官网验证、国家确认、联系方式可用、可审核的各阶段转化率；
- 非企业实体消耗验证预算的比例；
- 官网可达候选的国家解析覆盖率和准确率；
- 联系方式恢复率；
- 每个可审核客户的 Provider 请求、页面数、Token、耗时和估算成本；
- 每个未进入可审核状态的候选是否具有明确原因和人工下一步；
- Job 最终收敛率及重试、超时、取消的一致性。

## 4. 不可破坏的产品与安全边界

所有 QV 子项目必须保持以下不变量：

1. Mission、Radar 和浏览器研究只允许用户手动触发；
2. 没有任何路径自动接受候选、自动进入 CRM 或自动发送消息；
3. `unknown` 候选可以降序或待补证，但不得仅因未知而硬删除；
4. 历史快照和第三方页面不能提升为证明当前公司状态的 A 级官网证据；
5. 浏览器恢复只能由用户针对选定候选触发，并受页面数、时长、同域和网络出口策略限制；
6. 所有查询、持久化、Job 和审计事件继续携带 tenant scope；
7. 人工接受、拒绝和 CRM 状态优先于任何后到的自动计算；
8. 不用少量用户反馈自动改写线上规则或 Prompt。

## 5. 总体执行顺序

```text
QV-0 发布基线与事实收口
  -> QV-1 评测语料与真实 Mission 基线
      -> QV-2 结果质量与预算转化
          -> QV-3 用户审核与恢复工作流
              -> QV-4 外部试用运行与安全门禁
```

每个阶段必须独立形成可测试提交、审计证据和退出结论。前一阶段未通过时，不以增加后续功能掩盖失败。

## 6. QV-0：发布基线与事实收口

### 目标

建立唯一、可复现、可推送和可审计的代码基线，使本地运行版本、远端分支、迁移版本、计划状态和测试证据指向同一组提交。

### 范围

- 选择一个规范发布分支承载已验证的 Acquisition 与 Radar 提交；
- 明确本地 HEAD、远端 HEAD、数据库迁移 head 和 Docker 运行镜像之间的对应关系；
- 更新 Phase 2/QV 相关文档中的完成状态、实际提交和剩余范围；
- 保留用户已有的无关工作区修改，不混入提交；
- 运行完整 Acquisition、Radar、Browser、Worker、迁移与安全回归；
- 保存测试日志、迁移 smoke、运行时截图和版本清单。

### 退出门禁

- 规范分支有明确 upstream；
- 工作区只保留已识别的用户无关修改；
- 数据库 current 与 head 一致；
- Web、Redis、Worker、Scheduler 使用同一版本；
- 全量适用测试通过，`git diff --check` 和秘密扫描通过；
- 文档不得仍把已实现功能标为未开始，也不得把未实现范围标为完成。

## 7. QV-1：评测语料与真实 Mission 基线

### 目标

把“感觉结果变好”变成可重复、可对比的质量报告，并冻结优化前基线。

### 语料设计

复用现有 `tests/fixtures/acquisition/global_quality/` 的 14 个脱敏样本，将总样本扩充到至少 50 个。样本必须覆盖：

- PE、MX、BR、CO、AR、CL、US、DE、ES、CN 等市场或跨境服务场景；
- `.com`、复合 ccTLD、通用化 ccTLD、跨国总部与目标市场分离；
- 经销商、进口商、批发商、维修网络和未知买家角色；
- 企业官网、媒体、目录、商会、政府、招聘页、品牌新闻页和占位域名；
- 首页有联系方式、仅联系页有联系方式、动态壳页面、官网不可达和 AI schema 失败；
- 英语、西班牙语、葡萄牙语以及信息稀疏页面。

每个样本保存脱敏 HTML/文本、原始 URL 类型、人工标签、预期国家、实体类型、联系路径、来源身份和是否应消耗验证预算。真实客户隐私、Cookie、Token 和页面脚本不得进入仓库。

### 真实运行基线

由用户手动启动 10–20 个 Mission。每个 Mission 记录：

- 查询数、Provider 返回数、有效命中数、被跳过数和去重数；
- 进入验证预算的候选及排序位置；
- 官网验证、国家解析、联系方式、AI 分析和最终状态；
- 真实 Provider 请求、页面数、Token、耗时和估算成本；
- 用户最终接受、拒绝、待补证及其原因。

### 退出门禁

- 至少 50 个版本化、脱敏、人工标注的回放样本；
- 至少 10 个完整手动 Mission 的冻结基线；
- 同一版本和相同输入重复执行得到一致的确定性指标；
- 报告能按国家、语言、Provider、实体类型和失败阶段分组；
- 基线报告只读，不根据评测结果自动修改生产规则。

## 8. QV-2：结果质量与预算转化

QV-2 分为三个可独立审核的切片，依次实施。

### QV-2A：全球国家、联系与新鲜度解析

- 将当前有限国家别名升级为版本化的 ISO 国家信号解析器；
- 正确处理复合 ccTLD、通用化 ccTLD、页面地址、电话区号和服务地区；
- 将总部国家、目标市场和联系国家保持为不同字段，不因目标 Mission 国家直接确认公司国家；
- 在首页无联系信息时，规划同域 `contact`、`contacto`、`ventas`、`sales`、`about` 等页面，仍受现有页面预算约束；
- 联系方式保存类型、规范化值、来源 URL 和 evidence ID；
- `data_recency` 根据 `retrieved_at`、`expires_at`、来源类型和证据状态计算，不再只要可用就固定为 90。

验收要求：

- 国家解析在标注语料上的精确率至少 95%，适用样本召回率至少 80%；
- 通用化 `.co` 等场景不得被 ccTLD 单独确认；
- 联系方式恢复率相对冻结基线提高至少 15 个百分点；
- 所有新鲜度边界用冻结时间测试验证。

### QV-2B：实体预筛与验证预算预排序

- 保留高精度媒体、目录、政府和招聘路径规则；
- 产生 `company`、`non_company`、`unknown` 三态结果以及规则版本和支撑证据；
- 使用国家信号、实体类型、域名身份、产品词、买家词、来源质量和联系路径构建版本化预排序；
- 排序只决定有限验证预算的先后顺序，不改变人工终态，不直接删除 `unknown`；
- 对多语言和未知场景保持可回放行为；
- 在 Mission retrospective 中保存排序版本和 Top N 选择原因。

验收要求：

- 高置信非企业分类精确率至少 95%；
- 当 Provider 原始顺序的 `precision@max_verify` 低于 70% 时，排序后必须达到至少 70% 且提高至少 10 个百分点；原始顺序已经达到 70% 时，排序后的回退不得超过 2 个百分点，且验证请求数和估算成本不得增加；
- `unknown` 硬删除数为 0；
- 同一输入、规则版本和预算得到相同排序。

### QV-2C：有界恢复与真实用量

- 保留现有官网失败退避、一次 schema 延迟重分析和 Mission watchdog；
- 对检测到 JS 壳页面或静态抓取策略明确阻止的候选，提供用户手动触发的隔离浏览器恢复；
- 普通空页面不得误标为 `requires_browser`；
- 浏览器恢复不自动接受候选，不自动改变 CRM，不突破 URL 安全与同域策略；
- 在 Provider 适配器边界记录每次真实请求的用途、状态、页面数、Token、耗时和估算成本；
- Mission 只展示聚合值，详细请求日志保持 tenant scope 并进行敏感字段脱敏。

验收要求：

- 每个候选的 AI 延迟重分析最多一次；
- 重试、早到 Scheduler delivery、暂停、取消和 watchdog 竞争均收敛到单一终态；
- 测试环境中 Provider 真实调用数与用量事件数完全一致；
- 手动浏览器恢复的未授权调用数、跨租户访问数和自动触发数均为 0。

## 9. QV-3：用户审核与恢复工作流

### 目标

让用户首先看到业务产出和下一步，而不是理解 Job、Provider 或内部错误码。

### Mission 详情

显示一致的业务漏斗：

```text
发现 -> 企业身份通过 -> 官网验证 -> 国家确认 -> 联系方式可用 -> 可审核 -> 已进入 CRM
```

漏斗的每个数字必须来自统一 ViewModel/BusinessResultResolver，不允许模板自行重新计算。执行状态和业务结果并列显示：即使部分 Job 失败，只要保留候选或证据，就突出“部分结果可用”，而不是只展示红色失败。

### 候选操作

候选按“可审核、待补证、已排除”分组。每个未完成候选必须显示一个主原因和一个对应操作：

- 官网不可达：提供官网或重新验证；
- 来源身份不一致：查看第三方证据并补充官网；
- 国家待确认：查看或补充国家证据；
- AI schema 失败：查看有限重分析状态或手动重新验证；
- 动态页面：手动启动受控浏览器恢复；
- 联系方式缺失：手动搜索同域联系页；
- 非企业实体：查看分类依据并保留人工纠正入口。

证据详情按“来源 -> 观察事实 -> 推断 -> 门禁 -> 判定”展示，并明确区分事实、推断和未知项。页面展示任务预算上限、实际消耗、剩余预算和成本，不展示密钥、完整 Prompt 或页面正文。

### 退出门禁

- 100% 的终态非可审核候选具有明确原因和可执行操作，确实无操作时明确标注原因；
- 漏斗数字与数据库事实、通知和 retrospective 完全一致；
- 键盘操作、焦点、标签、对比度和非颜色状态表达通过可访问性检查；
- Playwright 覆盖手动 Mission、部分结果、补证、浏览器恢复、接受和拒绝；
- 自动 CRM、自动外联和自动定时运行计数保持为 0。

## 10. QV-4：外部试用运行与安全门禁

### 目标

在不扩大产品自动化范围的前提下，使系统可以被少量试用用户可靠运行和恢复。

### 运行能力

- 继续提供 `/health/live` 与 `/health/ready`；
- 增加受权限保护的运行状态页面，显示 Web、数据库、Redis、Worker、Scheduler、队列积压、最后心跳和迁移版本；
- 提供失败 Mission 和停滞 Job 的只读诊断，以及明确的人工恢复入口；
- 完成备份、恢复、前向迁移和回滚替代流程演练；
- 对队列重复投递、Worker 重启、Redis 短暂不可用和超时竞争执行受控集成测试。

### 数据与安全治理

- 明确网页快照、联系方式、审计事件和用量事件的保存期限；
- 明确租户导出、删除和账户删除后的数据处理；
- 定义 owner/member 对 Mission、Radar、浏览器恢复、候选接受和 CRM 晋升的权限矩阵；
- 运行 SSRF、DNS rebinding、私网出口、重定向、CSRF、越权和敏感信息日志回归；
- 建立依赖和秘密扫描，并保存版本化安全证据。

### 退出门禁

- Web、Worker、Redis、数据库和 Scheduler 状态可被操作者判断；
- 备份恢复及迁移演练在隔离数据上通过；
- 跨租户读写、未授权浏览器运行、自动 CRM 和自动外联计数均为 0；
- 关键队列故障场景最终收敛且不会留下永久 `running` 或 `retrying` 状态；
- 发布证据能够从提交、迁移、镜像追溯到测试结果。

## 11. 端到端数据流

```text
用户手动启动 Mission
  -> Discovery 记录查询与真实命中
  -> Entity Triage 标注 company/non_company/unknown
  -> Versioned Ranking 分配有限验证预算
  -> Static Fetch 保存公开证据与来源身份
  -> Country/Contact/Freshness 确定性解析
  -> MiMo 只处理语义买家角色和产品相关性
  -> Gate + Score 生成可审核/待补证/排除
  -> Mission Funnel 汇总原因、预算和用量
  -> 用户人工补证、接受、拒绝或手动浏览器恢复
  -> 只有人工确认后才进入 CRM
```

Radar 继续保持独立手动入口。Radar 只把有引用依据的 dealer/distributor 关系转为 Acquisition `needs_evidence` 候选，随后复用同一套验证、判定和人工审核链路。

## 12. 测试与审计策略

每个子项目遵循测试先行并保存以下证据：

1. 纯函数单元测试：国家、联系、新鲜度、实体分类、排序和状态映射；
2. 版本化回放：至少 50 例，报告字段级差异和分组指标；
3. Repository/Service 集成：tenant scope、幂等、人工终态优先和用量写入；
4. Redis/RQ 受控集成：早到调度、重复投递、Worker 重启、暂停、取消和 watchdog；
5. Browser 安全测试：SSRF、重定向、私网、同域、Cookie/凭据隔离和预算；
6. 路由与 CSRF：所有人工变更入口；
7. Playwright：核心用户流程、错误恢复、可访问性和截图；
8. Alembic：空库升级、现有库升级、current/head 一致；
9. 全量回归、格式、类型、`git diff --check`、依赖和秘密扫描；
10. 真实 Mission 只由用户手动启动，验证脚本只读汇总结果。

## 13. 交付与分支策略

该方案包含多个独立子系统，不应塞入一个 PR。确认本设计后，分别生成并执行以下实施计划：

1. `QV-0 release baseline`；
2. `QV-1 evaluation baseline`；
3. `QV-2A country-contact-recency`；
4. `QV-2B entity-ranking`；
5. `QV-2C recovery-usage`；
6. `QV-3 operator workflow`；
7. `QV-4 external pilot gate`。

每个计划使用独立分支和 PR，包含明确迁移所有权、测试命令、审计证据和前序依赖。任何需要 migration 的切片只能在前一基线合并并重新确认 Alembic head 后创建前向迁移。

## 14. 最终通过标准

QV 计划完成时必须满足：

- 至少 50 个版本化评测样本和 10 个真实手动 Mission 基线；
- 可审核候选准确率至少 70%；
- 国家解析、实体分类和预排序达到各自门禁；
- 每个结果都能解释证据、事实、推断、门禁和下一步；
- 实际 Provider 用量、耗时和成本可以追溯；
- 所有后台 Job 最终收敛，无永久停滞状态；
- 用户仍然是 Mission、Radar、浏览器恢复、候选接受和 CRM 晋升的唯一触发者；
- 自动 CRM、自动外联、后台定时和跨租户访问均为 0；
- 发布分支、远端提交、迁移、运行镜像、文档和测试证据一致。

只有达到以上标准并由用户明确重新决策后，才讨论定时 Radar、更多数据 Provider 或外联自动化；它们不会因 QV 完成而自动启用。
